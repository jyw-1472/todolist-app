### S-01: 회원가입

**대응 UC:** UC-01
**관련 API:** `POST /api/auth/signup`

#### 사전 조건 (Precondition)

- 사용자가 서비스에 접속해 회원가입 화면을 열어 놓은 상태이다.
- 사용자는 아직 계정이 없다.

#### 기본 흐름 (Main Flow)

| 단계 | 행위자 | 설명 |
|------|--------|------|
| 1 | 사용자 | 이메일, 비밀번호, 이름을 입력하고 "가입하기" 버튼을 클릭한다. |
| 2 | 시스템 | 이메일 형식, 비밀번호 최소 조건, 이름 필수 여부를 클라이언트 측에서 1차 검증한다. |
| 3 | 시스템 | `POST /api/auth/signup` 요청을 서버로 전송한다. |
| 4 | 시스템 | 서버는 이메일 중복 여부를 DB에서 확인한다. |
| 5 | 시스템 | 비밀번호를 bcrypt(salt rounds ≥ 10)로 해시 처리하여 users 테이블에 저장한다. |
| 6 | 시스템 | 가입 성공 응답(201 Created)을 반환하고, 클라이언트는 로그인 화면으로 이동한다. |

#### 대안 흐름 (Alternative Flow)

| 조건 | 처리 | 에러 코드 |
|------|------|----------|
| 필수 필드(이메일·비밀번호·이름) 미입력 또는 형식 오류 | 서버가 400 응답을 반환하고, 클라이언트는 해당 필드에 오류 메시지를 표시한다. | `VALIDATION_ERROR` (400) |
| 이미 사용 중인 이메일 입력 | 서버가 409 응답을 반환하고, "이미 사용 중인 이메일입니다." 안내를 표시한다. | `DUPLICATE_EMAIL` (409) |
| 서버 내부 오류 발생 | 서버가 500 응답을 반환하고, 일반 오류 안내 메시지를 표시한다. | `INTERNAL_SERVER_ERROR` (500) |

#### 사후 조건 (Postcondition)

- users 테이블에 신규 레코드가 생성된다. (provider = 'local')
- 사용자는 로그인 화면으로 이동하여 방금 가입한 계정으로 로그인할 수 있다.

### S-02: 로그인

**대응 UC:** UC-02
**관련 API:** `POST /api/auth/login`

#### 사전 조건 (Precondition)

- 사용자가 회원가입을 완료한 상태이다.
- 사용자가 로그인 화면에 접근해 있다.

#### 기본 흐름 (Main Flow)

| 단계 | 행위자 | 설명 |
|------|--------|------|
| 1 | 사용자 | 이메일과 비밀번호를 입력하고 "로그인" 버튼을 클릭한다. |
| 2 | 시스템 | `POST /api/auth/login` 요청을 서버로 전송한다. |
| 3 | 시스템 | 서버는 이메일로 사용자를 조회하고, bcrypt로 비밀번호를 검증한다. |
| 4 | 시스템 | 검증 성공 시 Access Token(만료 15분)과 Refresh Token(만료 7일)을 발급한다. |
| 5 | 시스템 | Access Token과 Refresh Token을 모두 응답 바디로 전달한다. |
| 6 | 시스템 | 클라이언트는 Access Token과 Refresh Token을 Zustand 메모리에 저장하고 할일 목록 화면으로 이동한다. |

#### 대안 흐름 (Alternative Flow)

| 조건 | 처리 | 에러 코드 |
|------|------|----------|
| 이메일 또는 비밀번호 미입력 | 클라이언트에서 유효성 오류를 표시한다. | `VALIDATION_ERROR` (400) |
| 이메일이 존재하지 않거나 비밀번호 불일치 | 서버가 401 응답을 반환하고, "이메일 또는 비밀번호가 올바르지 않습니다." 메시지를 표시한다. | `UNAUTHORIZED` (401) |
| 서버 내부 오류 발생 | 서버가 500 응답을 반환하고, 일반 오류 안내 메시지를 표시한다. | `INTERNAL_SERVER_ERROR` (500) |

#### 사후 조건 (Postcondition)

- 클라이언트가 유효한 Access Token을 보유하여 인증이 필요한 API를 호출할 수 있는 상태가 된다.
- Access Token과 Refresh Token이 Zustand 메모리에 저장된다. (페이지 새로고침 시 소멸)
- 사용자는 할일 목록 화면으로 이동한다.

### S-03: 개인정보 수정

**대응 UC:** UC-03
**관련 API:** `GET /api/users/me`, `PATCH /api/users/me`

#### 사전 조건 (Precondition)

- 사용자가 로그인된 상태이다.
- 사용자가 내 정보 수정 화면에 접근한다.

#### 기본 흐름 (Main Flow)

| 단계 | 행위자 | 설명 |
|------|--------|------|
| 1 | 시스템 | `GET /api/users/me`를 호출하여 현재 이름을 화면에 미리 채운다. |
| 2 | 사용자 | 변경할 이름을 입력하거나, 비밀번호 변경을 원하면 현재 비밀번호·새 비밀번호·새 비밀번호 확인을 입력한다. |
| 3 | 사용자 | "저장" 버튼을 클릭한다. |
| 4 | 시스템 | `PATCH /api/users/me` 요청을 `Authorization: Bearer <access_token>` 헤더와 함께 전송한다. |
| 5 | 시스템 | 비밀번호 변경 요청인 경우 서버가 현재 비밀번호를 bcrypt로 검증한다. |
| 6 | 시스템 | 검증 통과 시 이름 또는 비밀번호(해시)를 업데이트하고 200 OK를 반환한다. |
| 7 | 시스템 | 클라이언트는 성공 안내 메시지를 표시하고 화면을 갱신한다. |

#### 대안 흐름 (Alternative Flow)

| 조건 | 처리 | 에러 코드 |
|------|------|----------|
| 변경 항목을 아무것도 입력하지 않음 | 클라이언트에서 "변경할 내용을 입력하세요." 오류를 표시한다. | `VALIDATION_ERROR` (400) |
| 현재 비밀번호가 일치하지 않음 | 서버가 401 응답을 반환하고, "현재 비밀번호가 올바르지 않습니다." 메시지를 표시한다. | `UNAUTHORIZED` (401) |
| Access Token 만료 상태로 요청 | 시스템이 자동으로 토큰 갱신(S-12) 후 재요청한다. 갱신 실패 시 로그인 화면으로 이동한다. | `UNAUTHORIZED` (401) |
| 서버 내부 오류 발생 | 서버가 500 응답을 반환하고, 일반 오류 안내 메시지를 표시한다. | `INTERNAL_SERVER_ERROR` (500) |

#### 사후 조건 (Postcondition)

- users 테이블의 name 또는 password 컬럼이 변경된 값으로 업데이트된다.
- 비밀번호를 변경한 경우 기존 세션은 유지되나, 이후 로그인 시 새 비밀번호를 사용해야 한다.

### S-04: 할일 등록

**대응 UC:** UC-04
**관련 API:** `POST /api/todos`

#### 사전 조건 (Precondition)

- 사용자가 로그인된 상태이다.
- 최소 1개 이상의 카테고리(기본 카테고리 포함)가 존재한다.
- 사용자가 할일 등록 화면을 열어 놓은 상태이다.

#### 기본 흐름 (Main Flow)

| 단계 | 행위자 | 설명 |
|------|--------|------|
| 1 | 시스템 | `GET /api/categories`를 호출하여 사용 가능한 카테고리 목록을 카테고리 선택 드롭다운에 표시한다. |
| 2 | 사용자 | 제목(필수), 설명(선택), 종료 예정일(선택), 카테고리(필수)를 입력·선택한다. |
| 3 | 시스템 | 종료 예정일이 오늘 이전 날짜인 경우 "오늘 이후 날짜를 권장합니다." 안내 메시지를 표시한다. (BR-06, 저장 차단은 하지 않음) |
| 4 | 사용자 | "등록" 버튼을 클릭한다. |
| 5 | 시스템 | `POST /api/todos` 요청을 `Authorization: Bearer <access_token>` 헤더와 함께 전송한다. |
| 6 | 시스템 | 서버는 필수 필드(제목, 카테고리)를 검증하고, 요청한 카테고리가 해당 사용자 소유임을 확인한다. |
| 7 | 시스템 | todos 테이블에 신규 레코드를 삽입하고 201 Created를 반환한다. |
| 8 | 시스템 | 클라이언트는 할일 목록 화면으로 이동하여 새로 등록된 항목을 표시한다. |

#### 대안 흐름 (Alternative Flow)

| 조건 | 처리 | 에러 코드 |
|------|------|----------|
| 제목 미입력 | 클라이언트에서 "제목은 필수입니다." 오류를 표시한다. | `VALIDATION_ERROR` (400) |
| 카테고리 미선택 | 클라이언트에서 "카테고리를 선택하세요." 오류를 표시한다. | `VALIDATION_ERROR` (400) |
| 요청한 category_id가 해당 사용자 소유가 아님 | 서버가 403 응답을 반환한다. | `FORBIDDEN` (403) |
| 요청한 category_id가 존재하지 않음 | 서버가 404 응답을 반환한다. | `RESOURCE_NOT_FOUND` (404) |
| Access Token 만료 | 시스템이 자동으로 토큰 갱신(S-12) 후 재요청한다. | `UNAUTHORIZED` (401) |

#### 사후 조건 (Postcondition)

- todos 테이블에 신규 레코드가 생성된다. (is_completed = false)
- 할일 목록 화면에 새로 등록된 항목이 종료 예정일 오름차순 정렬로 노출된다.

### S-05: 할일 수정

**대응 UC:** UC-05
**관련 API:** `GET /api/todos/:id`, `PATCH /api/todos/:id`

#### 사전 조건 (Precondition)

- 사용자가 로그인된 상태이다.
- 수정하려는 할일이 존재하며, 해당 사용자 소유이다.
- 사용자가 할일 수정 화면을 열어 놓은 상태이다.

#### 기본 흐름 (Main Flow)

| 단계 | 행위자 | 설명 |
|------|--------|------|
| 1 | 시스템 | `GET /api/todos/:id`를 호출하여 기존 제목·설명·종료 예정일·카테고리 값을 화면에 미리 채운다. |
| 2 | 사용자 | 제목, 설명, 종료 예정일, 카테고리 중 변경할 항목을 수정한다. |
| 3 | 사용자 | "저장" 버튼을 클릭한다. |
| 4 | 시스템 | `PATCH /api/todos/:id` 요청을 `Authorization: Bearer <access_token>` 헤더와 함께 전송한다. |
| 5 | 시스템 | 서버는 해당 할일이 요청 사용자 소유임을 확인하고 변경 내용을 검증한다. |
| 6 | 시스템 | todos 테이블의 해당 레코드를 업데이트하고 updated_at을 NOW()로 갱신 후 200 OK를 반환한다. |
| 7 | 시스템 | 클라이언트는 성공 안내를 표시하고 수정된 내용으로 화면을 갱신한다. |

#### 대안 흐름 (Alternative Flow)

| 조건 | 처리 | 에러 코드 |
|------|------|----------|
| 제목을 빈 값으로 저장 시도 | 클라이언트에서 "제목은 필수입니다." 오류를 표시한다. | `VALIDATION_ERROR` (400) |
| 카테고리를 선택하지 않은 상태로 저장 시도 | 클라이언트에서 "카테고리를 선택하세요." 오류를 표시한다. | `VALIDATION_ERROR` (400) |
| 요청한 할일이 존재하지 않음 | 서버가 404 응답을 반환한다. | `RESOURCE_NOT_FOUND` (404) |
| 요청한 할일이 타 사용자 소유임 | 서버가 403 응답을 반환한다. | `FORBIDDEN` (403) |
| Access Token 만료 | 시스템이 자동으로 토큰 갱신(S-12) 후 재요청한다. | `UNAUTHORIZED` (401) |

#### 사후 조건 (Postcondition)

- todos 테이블의 해당 레코드가 수정된 값과 갱신된 updated_at으로 업데이트된다.
- 할일 목록 화면에 수정된 내용이 반영된다.

### S-06: 할일 삭제

**대응 UC:** UC-06
**관련 API:** `DELETE /api/todos/:id`

#### 사전 조건 (Precondition)

- 사용자가 로그인된 상태이다.
- 삭제하려는 할일이 존재하며, 해당 사용자 소유이다.
- 사용자가 할일 목록 또는 상세 화면에 있다.

#### 기본 흐름 (Main Flow)

| 단계 | 행위자 | 설명 |
|------|--------|------|
| 1 | 사용자 | 삭제하려는 할일의 "삭제" 버튼을 클릭한다. |
| 2 | 시스템 | "정말 삭제하시겠습니까?" 확인 다이얼로그를 표시한다. |
| 3 | 사용자 | "확인" 버튼을 클릭한다. |
| 4 | 시스템 | `DELETE /api/todos/:id` 요청을 `Authorization: Bearer <access_token>` 헤더와 함께 전송한다. |
| 5 | 시스템 | 서버는 해당 할일이 요청 사용자 소유임을 확인한다. |
| 6 | 시스템 | todos 테이블에서 해당 레코드를 삭제하고 204 No Content를 반환한다. |
| 7 | 시스템 | 클라이언트는 목록에서 해당 할일 카드를 제거하여 화면을 갱신한다. |

#### 대안 흐름 (Alternative Flow)

| 조건 | 처리 | 에러 코드 |
|------|------|----------|
| 확인 다이얼로그에서 "취소" 클릭 | 삭제 요청을 전송하지 않고 이전 화면으로 돌아간다. | - |
| 요청한 할일이 존재하지 않음 | 서버가 404 응답을 반환하고, 클라이언트는 목록을 재조회한다. | `RESOURCE_NOT_FOUND` (404) |
| 요청한 할일이 타 사용자 소유임 | 서버가 403 응답을 반환한다. | `FORBIDDEN` (403) |

#### 사후 조건 (Postcondition)

### S-07: 완료 처리 (완료 상태 토글)

**대응 UC:** UC-07
**관련 API:** `PATCH /api/todos/:id/complete`

#### 사전 조건 (Precondition)

- 사용자가 로그인된 상태이다.
- 대상 할일이 존재하며, 해당 사용자 소유이다.
- 사용자가 할일 목록 화면에 있다.

#### 기본 흐름 (Main Flow) — 미완료 → 완료

| 단계 | 행위자 | 설명 |
|------|--------|------|
| 1 | 사용자 | 미완료 상태의 할일 카드에서 완료 체크박스 또는 "완료" 버튼을 클릭한다. |

| 단계 | 행위자 | 설명 |

| 1 | 사용자 | 완료 상태의 할일 카드에서 완료 체크박스 또는 "완료 취소" 버튼을 클릭한다. |
| 2 | 시스템 | `PATCH /api/todos/:id/complete` 요청을 전송한다. |
| 3 | 시스템 | 서버는 is_completed 값을 false로 토글하고 200 OK를 반환한다. |
| 4 | 시스템 | 클라이언트는 해당 카드를 미완료 상태로 표시하고 화면을 갱신한다. |

### S-11: 로그아웃

**대응 UC:** UC-11
**관련 API:** `POST /api/auth/logout`

#### 사전 조건 (Precondition)

- 사용자가 로그인된 상태이다. (유효한 Access Token과 Refresh Token 보유)
- 사용자가 로그아웃 버튼에 접근할 수 있는 상태이다.

#### 기본 흐름 (Main Flow)

| 단계 | 행위자 | 설명 |
|------|--------|------|
| 1 | 사용자 | 헤더 또는 메뉴에서 "로그아웃" 버튼을 클릭한다. |
| 2 | 시스템 | `POST /api/auth/logout` 요청을 `Authorization: Bearer <access_token>` 헤더와 함께 전송한다. |
| 3 | 시스템 | 서버는 요청 바디의 Refresh Token을 무효화(DB에서 삭제 또는 블랙리스트 처리)한다. |
| 4 | 시스템 | 서버는 200 OK를 반환한다. |
| 5 | 시스템 | 클라이언트는 Zustand 상태에서 Access Token과 Refresh Token을 파기하고 인증 정보를 초기화한다. |
| 6 | 시스템 | 클라이언트는 로그인 화면으로 이동한다. |

#### 대안 흐름 (Alternative Flow)

| 조건 | 처리 | 에러 코드 |
|------|------|----------|
| Access Token이 이미 만료된 상태에서 로그아웃 시도 | 클라이언트는 먼저 토큰 갱신(S-12)을 시도하거나, 갱신 없이 클라이언트 측 상태만 초기화하고 로그인 화면으로 이동한다. | `UNAUTHORIZED` (401) |
| 서버 내부 오류 발생 | 서버 오류와 무관하게 클라이언트 측 Access Token을 파기하고 로그인 화면으로 이동한다. | `INTERNAL_SERVER_ERROR` (500) |

#### 사후 조건 (Postcondition)

- 서버의 Refresh Token이 무효화된다.
- 클라이언트의 Access Token과 Refresh Token이 Zustand에서 파기된다.
- 이후 인증이 필요한 API 요청 시 재로그인이 필요하다.

### S-12: 토큰 갱신

**대응 UC:** UC-12
**관련 API:** `POST /api/auth/refresh`

#### 사전 조건 (Precondition)

- 사용자의 Access Token이 만료된 상태이다.
- 사용자의 Refresh Token이 유효한 상태로 Zustand 메모리에 저장되어 있다.

#### 기본 흐름 (Main Flow)

| 단계 | 행위자 | 설명 |
|------|--------|------|
| 1 | 시스템 | 인증이 필요한 API 요청 후 서버로부터 401 응답을 수신한다. |
| 2 | 시스템 | TanStack Query 또는 Axios 인터셉터가 자동으로 `POST /api/auth/refresh`를 호출한다. (Zustand에서 Refresh Token을 읽어 `Authorization: Bearer` 헤더에 포함) |
| 3 | 시스템 | 서버는 Refresh Token의 유효성을 검증한다. |
| 4 | 시스템 | 검증 성공 시 새로운 Access Token을 발급하고 200 OK와 함께 응답 바디로 반환한다. |
| 5 | 시스템 | 클라이언트는 새 Access Token을 Zustand 상태에 저장한다. |
| 6 | 시스템 | 이전에 실패했던 원래 API 요청을 새 Access Token으로 재시도한다. |

#### 대안 흐름 (Alternative Flow)

| 조건 | 처리 | 에러 코드 |
|------|------|----------|
| Refresh Token도 만료된 경우 | 서버가 401 응답을 반환한다. 클라이언트는 상태를 초기화하고 "세션이 만료되었습니다. 다시 로그인해 주세요." 안내 후 로그인 화면으로 이동한다. | `UNAUTHORIZED` (401) |
| Refresh Token이 유효하지 않거나 무효화된 경우 | 서버가 401 응답을 반환하고, 클라이언트는 로그인 화면으로 이동한다. | `UNAUTHORIZED` (401) |
| 서버 내부 오류 발생 | 서버가 500 응답을 반환하고, 클라이언트는 로그인 화면으로 이동한다. | `INTERNAL_SERVER_ERROR` (500) |

#### 사후 조건 (Postcondition)

- 클라이언트가 새로운 유효한 Access Token을 보유하게 된다.
- 사용자는 로그인 화면으로 이동하지 않고 작업을 계속 진행할 수 있다.

| 3 | 사용자 | 본인 확인을 위해 현재 비밀번호를 입력하고 "탈퇴" 버튼을 클릭한다. |
| 4 | 시스템 | `DELETE /api/users/me` 요청을 `Authorization: Bearer <access_token>` 헤더와 현재 비밀번호를 요청 바디에 포함하여 전송한다. |
| 5 | 시스템 | 서버는 현재 비밀번호를 bcrypt로 검증하여 본인 확인을 수행한다. |
| 6 | 시스템 | 검증 성공 시 DB 트랜잭션 내에서 해당 사용자의 todos, 사용자 정의 categories, users 레코드를 순서대로 삭제한다. (ON DELETE CASCADE 활용) |
| 7 | 시스템 | 204 No Content를 반환한다. |
| 8 | 시스템 | 클라이언트는 Access Token을 파기하고 "탈퇴가 완료되었습니다." 안내 메시지 후 서비스 초기 화면(회원가입 또는 로그인)으로 이동한다. |

#### 대안 흐름 (Alternative Flow)

| 조건 | 처리 | 에러 코드 |
|------|------|----------|
| 경고 다이얼로그에서 "취소" 클릭 | 탈퇴 요청을 전송하지 않고 이전 화면으로 돌아간다. | - |
| 비밀번호 미입력 | 클라이언트에서 "비밀번호를 입력하세요." 오류를 표시한다. | `VALIDATION_ERROR` (400) |
| 입력한 비밀번호가 일치하지 않음 | 서버가 401 응답을 반환하고, "비밀번호가 올바르지 않습니다." 메시지를 표시한다. | `UNAUTHORIZED` (401) |
| Access Token 만료 | 시스템이 자동으로 토큰 갱신(S-12) 후 재요청한다. | `UNAUTHORIZED` (401) |
| 서버 내부 오류 발생 | 서버가 500 응답을 반환하고, "처리 중 오류가 발생했습니다. 잠시 후 다시 시도해 주세요." 메시지를 표시한다. | `INTERNAL_SERVER_ERROR` (500) |

#### 사후 조건 (Postcondition)

- users, todos, 사용자 정의 categories 테이블에서 해당 사용자와 관련된 모든 레코드가 즉시 삭제된다.
- 기본 카테고리(시스템 소유, user_id = NULL)는 삭제되지 않는다.
- 해당 계정으로의 로그인이 불가능해진다.
- 기존 Access Token 및 Refresh Token이 모두 무효화된다.

## 3. 시나리오 간 연계 흐름

### 연계 흐름 1: 신규 사용자의 첫 할일 등록까지의 전체 흐름

> 처음 서비스를 접하는 신규 사용자 김민준이 회원가입부터 첫 번째 할일을 등록하기까지의 흐름이다.

```
[S-01] 회원가입
  - 이메일, 비밀번호, 이름 입력 후 가입 완료
  - users 테이블에 신규 레코드 생성
        |
        v
[S-02] 로그인
  - 가입한 이메일·비밀번호로 로그인
  - Access Token + Refresh Token 발급
  - 할일 목록 화면으로 이동 (목록은 비어 있음)
        |
        v
[S-09] 카테고리 추가 (선택)
  - 기본 카테고리 외 사용자 정의 카테고리("업무", "개인") 생성
  - categories 테이블에 신규 레코드 생성
        |
        v
[S-04] 할일 등록
  - 제목: "팀 미팅 자료 준비", 카테고리: "업무", 종료 예정일: 2026-05-15 입력
  - todos 테이블에 신규 레코드 생성
  - 할일 목록 화면에 첫 번째 항목 표시
```

---

### 연계 흐름 2: 할일 관리 일상 흐름 (조회 → 완료 처리 → 수정)

> 기존 사용자 이수아가 매일 할일을 확인하고 완료 처리하거나 수정하는 흐름이다.

```
[S-02] 로그인 (또는 S-12 토큰 자동 갱신으로 세션 유지)
  - 할일 목록 화면으로 이동
        |
        v
[S-08] 할일 목록 조회
  - 카테고리: "연구", 완료 여부: false 필터 적용
  - 미완료 연구 관련 할일만 종료 예정일 오름차순으로 표시
        |
        v
[S-07] 완료 처리
  - "논문 초안 작성" 할일의 완료 체크박스 클릭
  - is_completed = true로 토글
  - 목록 화면에서 완료 상태로 변경됨
        |
        v
[S-05] 할일 수정 (필요 시)
  - "발표 준비" 할일의 종료 예정일을 2026-05-20에서 2026-05-22로 변경
  - todos 테이블의 due_date와 updated_at 갱신
        |
        v
[S-11] 로그아웃
  - 작업 완료 후 로그아웃
  - Zustand에서 Access Token·Refresh Token 파기, 서버 Refresh Token 무효화
```

---

### 연계 흐름 3: 계정 관리 흐름 (개인정보 수정 → 카테고리 정리 → 회원 탈퇴)

> 서비스를 더 이상 사용하지 않기로 결정한 사용자가 최종 탈퇴까지 진행하는 흐름이다.

```
[S-02] 로그인
  - 기존 계정으로 로그인
        |
        v
[S-03] 개인정보 수정 (선택)
  - 이름 변경 또는 비밀번호 변경
        |
        v
[S-06] 할일 삭제 (필요 시)
  - 특정 카테고리에 속한 할일을 삭제
        |
        v
[S-10] 카테고리 삭제 (필요 시)
  - 할일이 없는 사용자 정의 카테고리를 삭제
  - 기본 카테고리는 삭제 불가 (DEFAULT_CATEGORY_IMMUTABLE)
        |
        v
[S-13] 회원 탈퇴
  - "회원 탈퇴" 버튼 클릭 → 경고 다이얼로그 확인
  - 현재 비밀번호 입력으로 본인 확인
  - 사용자·할일·사용자 정의 카테고리 즉시 삭제
  - 로그인 화면으로 이동
```

## 4. 비즈니스 규칙 - 시나리오 매핑

| 비즈니스 규칙 | 적용 시나리오 | 시스템 처리 방식 |
|-------------|-------------|--------------|
| BR-01: 이메일 고유 | S-01 | DUPLICATE_EMAIL(409) 반환 |
| BR-02: 인증된 사용자만 CRUD | S-04 ~ S-13 (인증 필요 전체) | Access Token 미보유 시 UNAUTHORIZED(401) 반환 |
| BR-03: 본인 데이터만 접근 | S-04 ~ S-10 | API 레벨에서 user_id 일치 여부 검증, 불일치 시 FORBIDDEN(403) 반환 |
| BR-04: 할일 등록 시 카테고리 필수 | S-04 | 카테고리 미선택 시 VALIDATION_ERROR(400) 반환 |
| BR-05: 기본 카테고리 수정·삭제 불가 | S-10 | DEFAULT_CATEGORY_IMMUTABLE(403) 반환 |
| BR-06: 신규 등록 시 오늘 이후 날짜 권장 | S-04 | 과거 날짜 입력 시 권장 안내 표시 (저장은 허용) |
| BR-07: 완료 후 재조회 및 취소 가능 | S-07, S-08 | is_completed 토글 방식으로 구현 |
| BR-08: 할일 존재하는 카테고리 삭제 불가 | S-10 | CATEGORY_HAS_TODOS(409) 반환 |
